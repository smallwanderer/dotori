# v1.2 변경 사항

검증 기준: 마지막 커밋 `eed11fe`(`RAG Runtime Container Lifecycle Improved`) 대비 현재 작업 트리의 전체 변경분(스테이징·미스테이징·신규 파일 포함).

지난 커밋이 RAG 런타임 컨테이너를 Docker CLI로 직접 관리하는 생명주기를 도입했다면, 이번 v1.1 작업은 이를 바탕으로 **평상시 기동과 유지보수 작업을 분리하고 배포 상태를 명시적으로 관리하는 운영 흐름**을 구축한다.

> 이 문서는 아직 커밋되지 않은 현재 작업 트리를 기준으로 한다. 이후 코드가 변경되면 내용도 다시 검증해야 한다.

## 1. RAG 런타임 이미지와 내부 주소 통합

- 기존 `llama-rag/`와 `vllm-rag/` 빌드 디렉터리를 `llm-runtime/` 하나로 통합했다.
  - `llm-runtime/llama.Dockerfile`
  - `llm-runtime/vllm.Dockerfile`
  - 공용 `llm-runtime/start.sh`
- 런타임별 args 환경변수 `LLAMA_RAG_ARGS_FILE` / `VLLM_RAG_ARGS_FILE`을 `RAG_RUNTIME_ARGS_FILE` 하나로 통합했다(`runtime_lifecycle.RUNTIME_ARGS_ENV`).
- 두 런타임 모두 Docker 네트워크 별칭 `rag-runtime`을 사용하도록 내부 기본 URL을 `http://rag-runtime:8080`으로 통일했다. 이에 맞춰 `.env.example`, 플래너 및 RAG 요청 설정의 기본값도 변경했다.
- `runtime_lifecycle.py`는 공용 빌드 컨텍스트에서 런타임별 Dockerfile을 `docker build -f`로 선택한다.
- 대형 모델의 콜드 스타트를 고려해 런타임 대기 제한과 Docker health start period를 각각 llama.cpp 900초, vLLM 1200초로 늘렸다.
- 공용 `start.sh`는 args 파일의 CRLF를 제거한 뒤 런타임 프로세스에 전달한다.

## 2. 배포 플랜 도입 (`installation/deployment.py`)

- `DeploymentPlan`과 `WorkerSpec` 데이터클래스로 코어 서비스, 워커 활성 여부, 큐·동시성·의존성, 로컬 RAG 런타임 및 네트워크 접근 모드를 명시적으로 모델링했다.
- `rag`, `search`, `basic` 모드에 따라 필요한 워커를 결정한다.
  - `rag`: embedding / search / recovery와, 검증된 런타임이 있을 때만 rag-worker
  - `search`: embedding / search / recovery
  - `basic`: AI 워커 없음
- Compose 기동에 성공한 뒤 최종 플랜을 `data/config/deployment_scopes/<scope>/deployment_plan.json`에 원자적으로 기록하며, `install.py --status`와 `--json-output`에서 조회할 수 있다.
- `compose_up_command()`로 일반 기동의 `--no-build`와 유지보수 재빌드의 `--build --force-recreate` 명령 생성을 분리했다.

## 3. `install.py` / `start.bat` 운영 명령 재설계

기존 `--stop`은 Compose 컨테이너와 네트워크를 내리는 종료 동작이었다. 이제 일시정지, 완전 종료, 재시작, 재빌드를 구분한다.

| 옵션 | 동작 |
|---|---|
| `--stop` | Compose 서비스와 관리형 LLM 런타임을 정지하되 컨테이너·이미지·모델 캐시는 유지 |
| `--shutdown` | Compose 컨테이너·관리형 LLM 런타임 컨테이너·네트워크를 제거하되 데이터·설정·이미지·모델 캐시는 유지 |
| `--restart` | 서비스를 일시정지한 뒤 기존 이미지와 활성 런타임 generation으로 재기동 |
| `--rebuild` | 앱 이미지를 재빌드·강제 재생성하고 LLM 런타임 이미지도 다시 빌드한 뒤 검증 |

- 일반 `run_services()`와 `install.py --run`은 `docker compose up --no-build`를 사용한다. LLM 런타임도 이미지 재빌드를 수행하는 `apply()` 대신, 기존 컨테이너를 시작하거나 기존 이미지에서 컨테이너만 복원하는 `resume()`을 사용한다.
- `resume()`은 활성 generation과 기존 컨테이너의 runtime/generation 라벨이 일치하는지 확인하며, 이미지가 없거나 generation이 다르면 유지보수 재빌드를 안내하고 중단한다.
- RAG 모드의 초기 Compose 기동에서는 `rag-worker`를 제외한다. 런타임 health 및 endpoint 검증이 끝난 뒤에만 별도로 기동하며, 검증 실패 시 코어 서비스는 유지하되 RAG는 중지 상태로 남긴다.
- `start.bat`의 주 메뉴를 8개 항목으로 정리하고, Restart / Rebuild / Full Shutdown / Remove LLM Runtime을 `Maintenance` 하위 메뉴로 묶었다. Windows 콘솔은 시작 시 UTF-8 코드 페이지로 전환한다.
- 미사용 카탈로그 조회 CLI인 `--list-llm-models`, `--search-llm`, `--show-llm`과 관련 `install.py` 헬퍼를 제거했다.

## 4. 레거시 런타임 설정 스테이징 도입

- `config_store.stage_legacy_runtime_generation()`을 추가했다.
- generation 도입 이전의 flat `llm_runtime.json`과 런타임별 args 파일을 감지하면, 내용 해시로 안정적인 `legacy-<hash>` generation을 만들고 `runtime.json` 및 LF 형식의 `runtime.args`를 스테이징한다.
- 스테이징만으로 활성 설정을 덮어쓰지 않도록 설계했다.

현재 작업 트리에는 자동 마이그레이션 완료 경로가 아직 연결되지 않은 제한이 있다. 일반 RAG 기동은 레거시 generation을 만든 뒤 `resume()`으로 런타임을 검증하지만, `resume()`은 `commit_active_runtime_config()`를 호출하지 않는다. 그 결과 기존 flat 설정의 활성 포인터에는 `generation_id`가 기록되지 않고, 뒤이어 만드는 최종 배포 플랜도 해당 런타임을 활성 상태로 인식하지 못해 `rag-worker`를 켜지 않는다. 따라서 현 상태를 “구버전 사용자가 별도 조치 없이 자동 업그레이드된다”고 설명해서는 안 되며, 릴리스 전에 검증 성공 후 활성 generation을 커밋하는 경로를 보완해야 한다.

## 5. `docker-compose.yml` 운영 구조 정리

- YAML 앵커 `x-dotori-app`으로 app, embedding-worker, search-worker, rag-worker, recovery-worker가 공유하는 이미지·빌드 설정을 한곳으로 모았다.
- 기존 서비스의 `restart: always`를 `restart: unless-stopped`로 바꿔 사용자가 일시정지한 컨테이너가 Docker 재시작 후 자동으로 되살아나지 않도록 했다.
- `rag-worker`에 `managed-rag` profile을 추가해 런타임 검증 전 일반 Compose 기동에서 제외할 수 있게 했다.
- `rag-runtime` 네트워크를 외부 사전 생성 네트워크에서 Compose가 생성·관리하는 명시적 bridge 네트워크(`dotori-runtime`)로 변경했다. LLM 런타임 생명주기 관리자도 동일한 네트워크를 보장한다.

## 6. 모델 선택 UI와 카탈로그 메타데이터 개선

- `selection.py`에 `rank_manual_candidates()`를 추가해 수동 선택 화면의 표시 순서와 실제 선택 가능 여부가 동일한 FIT → RISKY 우선순위를 사용하도록 했다.
- `detect_llm_runtime.py`의 수동 선택 화면에 20개 단위 페이지네이션, 이전/다음 이동, 인덱스 선택을 추가했다.
- `cli.render_table()`을 추가해 ANSI 색상 적용 후에도 열 정렬이 유지되는 공용 테이블 렌더링을 제공한다.
- 수동 선택 표에는 예상 RAM/VRAM과 예상 decode TPS를 함께 표시한다.
- `tools/model-config.py`가 Transformers config와 GGUF header에서 `head_dim`을 추출하도록 확장했다. 값이 없으면 다음 순서로 결정한다.
  1. config/GGUF의 명시값
  2. 알려진 아키텍처 기본값(Gemma 3/4, Qwen 3 계열)
  3. `hidden_size // num_attention_heads` 산술 유도
- 명시값이 아닌 경우 해석 방식을 `head_dim_resolution`에 기록하고, 마지막 산술 유도를 사용한 경우에만 검토용 `head_dim_warning`을 추가한다.
- 관련 Gemma 3/4 및 Qwen 3/3.5 카탈로그 항목에 실제 `head_dim` 값을 보강했다.

## 7. 안정성·재현성·오프라인 운영 개선

- `install.py`의 명령 실행 헬퍼와 `runtime_lifecycle.py`, `runtime_probe.py`의 Docker 서비스 조회, `network_access/compose.py`의 subprocess 출력 디코딩에 UTF-8 및 대체 오류 처리를 적용해 Windows cp949 콘솔에서의 디코딩 실패를 방지했다.
- 런타임 generation의 args 파일을 항상 LF로 기록하고, 후보 런타임 검증 실패 시 삭제 전에 최근 컨테이너 로그를 결과 메시지에 보존한다.
- 외부 접속과 프록시 보안에 쓰이는 6개 설정을 `DOTORI_DJANGO_*` 네임스페이스로 통일했다: allowed hosts, CSRF trusted origins, secure proxy header, SSL redirect, session cookie secure, CSRF cookie secure. `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, HSTS 등 다른 Django 설정은 기존 이름을 유지한다.
- `requirements.web.txt`, `requirements.ai.txt`, `requirements.dev.txt`의 범위형 버전을 정확한 버전으로 고정하고, AI 의존성에 `torch`를 명시했다.
- `app/Dockerfile`에 Dockerfile 1.7 문법과 apt/pip BuildKit 캐시 마운트를 적용했다.
- `app/templates/base.html`에서 Google Fonts 외부 요청을 제거하고 Pretendard를 우선하는 시스템 폰트 스택으로 대체했다.
- 더 이상 사용하지 않는 빈 `dotori` 플레이스홀더 파일과 기존 `llama-rag/`, `vllm-rag/` 빌드 파일을 제거했다.

---

이번 변경의 핵심은 **매번 이미지를 재빌드하던 설치 중심 실행 경로를, 빠른 일상 기동과 명시적인 유지보수 작업이 분리된 운영 도구로 전환한 것**이다. 동시에 배포 모드와 워커 구성을 파일로 남기고, 검증된 단일 RAG 런타임이 준비된 뒤에만 `rag-worker`를 연결하도록 운영 안전성을 높였다.
