# Core

> 이전: [설계 원칙](../principles.md) · 다음: [등록부](./registry.md)

이 문서는 Dotori Core를 이루는 계정, 워크스페이스, 파일 블록이 소유하는 상태와 서비스 경계를 설명합니다. Dotori Core는 사용자와 워크스페이스, 파일의 저장과 권한을 소유하는 커널입니다. 하나의 컨테이너 이름을 뜻하지 않으며, 자료 유형별 처리 알고리즘을 알지 않는 것을 원칙으로 합니다. 이 원칙에서 벗어난 현재의 예외는 [차이와 과제](../gaps.md)에 기록합니다.

웹 UI와 CLI API는 여러 블록을 호출하는 진입점이자 조합 계층이며 Core 도메인 자체와 구분합니다.

| 블록 | 소유하는 상태 | 코드 위치 |
| --- | --- | --- |
| B1 계정 | 사용자, 인증 수단 (`accounts_*`) | `app/accounts/` |
| B2 워크스페이스 | 협업 단위, 멤버십 (`workspaces_*`) | `app/workspaces/` |
| B3 파일 | 폴더 트리, 업로드 원본, 작업 로그, 저장 용량 (`files_*`) | `app/files/` |

B3과 B4의 경계는 원본과 결과입니다. 원본이 사라지면 결과도 무효가 되지만, 결과가 없어도 원본은 온전합니다.

## 의존 방향

Core 안의 의존은 한 방향입니다. 파일(B3)은 워크스페이스(B2)를 참조하고, 워크스페이스는 계정(B1)을 참조합니다. 반대 방향의 참조는 없습니다.

```mermaid
flowchart LR
    B3["B3 파일"] --> B2["B2 워크스페이스"] --> B1["B1 계정"]
```

## 블록별 진입점

다른 블록은 상태를 직접 바꾸지 않고 각 블록의 서비스 함수를 호출합니다.

| 블록 | 서비스 | 맡는 일 |
| --- | --- | --- |
| B1 계정 | `services`, `cli_tokens`, `legacy_tokens` | 로컬 프로필 만들기, 이메일 변경과 인증 메일, CLI 토큰의 발급과 인증, 이전 방식 토큰의 인증 |
| B2 워크스페이스 | `services` | 워크스페이스 만들기, 초대 코드와 초대의 발급·수락, 멤버 역할 변경과 제거, 계정 삭제 때 개인 데이터 정리 |
| B3 파일 | `services/file_service`, `services/storage`, `services/access` | 폴더 만들기와 휴지통 이동·복원·영구 삭제, 업로드 검증과 용량 확인과 저장, 멤버십에 따른 조회·수정 권한 판정 |

워크스페이스에는 개인(personal)과 팀(team) 두 종류가 있고, 멤버십의 역할은 관리자(admin)와 일반 멤버(member)입니다.

## 계정이 만들어질 때

계정 하나가 만들어지면 나머지 상태가 시그널로 이어서 만들어집니다. 각 단계는 자기 블록이 정한 규칙이며, 앞 블록은 뒤 블록을 모릅니다.

```mermaid
flowchart LR
    U["계정 생성<br/>B1"] -- "시그널" --> W["개인 워크스페이스와<br/>관리자 멤버십 생성<br/>B2"]
    W -- "시그널" --> S["저장 용량 기록 생성<br/>B3"]
```

## 파일 변경과 저장 용량

워크스페이스의 저장 용량(`UserStorage.used_size`)은 파일 원본(`FileBlob`)이 저장되고 삭제될 때 함께 늘고 줄어듭니다. 이 갱신은 `FileBlob`의 시그널이 맡으므로 원본을 만들거나 지우는 경로가 무엇이든 사용량이 맞춰집니다. 시그널은 사용량을 읽어 계산한 뒤 쓰지 않고 데이터베이스 안에서 직접 더하고 빼므로, 동시에 여러 건을 저장해도 합계가 어긋나지 않습니다. 모델 인스턴스를 거치지 않는 쓰기(`update`, `bulk_create` 등)는 시그널을 호출하지 않아 사용량에 반영되지 않습니다.

한도 확인(`check_workspace_room`)은 저장 전에 한 번 하고, 확인과 저장 사이에 잠금은 없습니다. 같은 시점에 올라오는 업로드는 한도를 조금 넘을 수 있습니다.

## 진입점과 도메인의 구분

각 패키지의 `views`, `api_v1`, `urls`는 요청을 받아 서비스를 호출하는 조합 계층입니다. 도메인의 규칙은 서비스와 모델에 있고, 뷰는 여러 블록의 서비스를 한 요청에서 함께 호출할 수 있습니다.

- `accounts`의 `LocalProfileMiddleware`는 `LOGIN_REQUIRED`가 꺼져 있을 때 익명 요청을 로컬 프로필로 자동 인증합니다.
- `workspaces`의 `ActiveWorkspaceMiddleware`는 요청마다 활성 워크스페이스와 멤버십을 정하고, 지정이 없으면 개인 워크스페이스를 씁니다. 로컬 프로필 인증 뒤에 실행되어야 합니다.
- `files/sync_api`는 폴더 동기화 클라이언트가 호출하는 별도의 endpoint이며 자체 토큰 인증을 씁니다.

## 원칙에서 벗어난 현재의 예외

Core는 자료 유형별 처리를 알지 않는 것이 원칙이지만, `files/models.py`가 함수 안에서 등록부(B6)와 문서(B4)의 기능 활성 판정을 가져다 씁니다. 모듈 최상단의 import가 아니라서 import 검사를 통과하지만 의존은 존재합니다. 정리 계획은 [차이와 과제](../gaps.md)에 있습니다.

다루지 않는 것: 문서 블록 내부는 [문서](./documents.md)가, 쓰기 규칙은 [블록 경계 규칙](../crosscutting/boundaries.md)이 다룹니다.
